# 反向 SSH 隧道：让跳板机随时连回云 VM

## 背景

云 VM（Muse 运行环境）**不能接收外部入站连接**（SSH 直连被平台拦截），
但用户需要从一台有公网 IP 的跳板机（上海 ECS）随时 SSH 回到 VM 里操作。

解法：**反向 SSH 隧道**。VM 主动向跳板机建一条 `-R` 隧道，
跳板机监听本地端口，流量转发回 VM 的 sshd。

```
┌─────────────┐                         ┌──────────────┐
│   云 VM      │                         │  上海 ECS     │
│             │   ssh -R 22022:         │  (公网 IP)    │
│ sshd        │◄────────────────────────│ 127.0.0.1:   │
│ 127.0.0.1   │   127.0.0.1:2222        │ 22022 监听中  │
│ :2222       │                         │              │
└─────────────┘                         └──────────────┘
                    用户在跳板机上执行：
                    ssh -p 22022 song@127.0.0.1
```

## 架构要点

| 项目 | 说明 |
|------|------|
| VM 侧 sshd | 只监听 `127.0.0.1:2222`，禁密码、禁 root，只允许公钥 |
| 跳板机侧 | 监听 `127.0.0.1:22022`（loopback only，两端都不暴露公网） |
| 登录用户 | `song`（普通用户，sudo 需按需配置） |
| 保活 | `ServerAliveInterval=30`，看门狗每 15 分钟检查 |

## 难点：VM 会被平台随时替换

云 VM 重启/替换后，`/root`、`/etc`、`/usr/sbin/sshd`、用户账号**全部清空**，
只有 `/home/hatch` 持久。本项目用"pin 住恢复材料 + 幂等恢复脚本"解决：

| 恢复材料（放 `~/workspace` 持久目录） | 用途 |
|--------------------------------------|------|
| `.debs/` | openssh-server + sftp-server 的 .deb 包（apt 可能卡死，不用 apt） |
| `ssh-pinned/song_authorized_keys` | 登录公钥 |
| `ssh-pinned/sshd_host_keys/` | sshd 主机密钥（首次运行自动 pin，保证重启后 host key 不变） |
| `ssh-pinned/*_known_hosts` | 跳板机等主机的 host key（IP 常变但 key 不变） |
| `restore-after-reboot.sh` | 幂等恢复脚本：装 sshd → 建用户 → 写配置 → 启动 → 建隧道 |

看门狗每次运行先执行恢复脚本（无操作则静默），只在**实际重建了东西或失败**时才通知。

## 文件说明

| 文件 | 用途 |
|------|------|
| `restore-after-reboot.sh` | 幂等恢复脚本（核心） |
| `watchdog.md` | 看门狗任务说明（每 15 分钟执行一次） |
| `ssh-pinned/` | 恢复材料目录（含占位模板，真实密钥不进仓库） |
| `docs/setup.md` | 从零搭建步骤 |

## 安全说明

- 本仓库**不包含**任何私钥、真实公钥、host key、私有 IP 以外的敏感信息
- `ssh-pinned/` 下只有 `.example` 模板，真实文件按 `docs/setup.md` 在本地生成
- 隧道两端均为 loopback 监听，不暴露到公网
- sshd 禁密码、禁 root，仅公钥登录

## 退出码约定（restore-after-reboot.sh）

| 退出码 | 含义 |
|--------|------|
| 0 | 成功（无操作也返回 0） |
| 1 | 本地恢复失败（.deb 安装/sshd 启动失败） |
| 2 | 隧道重建失败（通常需要用户在平台审批新的出站 SSH 连接），不要反复重试 |
